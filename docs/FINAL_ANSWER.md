# Combining Predictive Utilization with Progressive Safety

Predictive pacing should be an advisory demand estimator, not a provider command path. Estimate pickup probability with smoothing over historical and recent observations, model in-flight ringing calls and connected-agent turnover, and include setup latency, provider health, and current campaign limits. Convert the desired expected agent occupancy into a recommended attempt count, then explain the estimate and its uncertainty.

Every recommendation must pass through an independent Safety Controller that reads current campaign state. It caps the batch by actual eligible agent capacity, active calls, per-agent ownership, borrower reservation status, campaign pause/emergency stop, provider health, and circuit-breaker state. If predictive confidence or provider health is poor, reduce the batch or fall back to progressive one-to-one allocation. Reserve agent and borrower resources before provider initiation, use leases for abandoned work, and reconcile unknown initiation outcomes before retrying. This preserves utilization as an optimization objective while keeping safety invariants as non-configurable gates.

## What Breaks as the System Scales

- **100 agents:** the first constraint is likely the process-local coordination boundary and synchronous in-memory repository work, not the pacing calculation. A restart loses campaign state and any second process has a separate lock set. Keep this scale single-process for the prototype, or move to durable conditional writes and shared idempotency before adding instances.
- **1,000 agents:** serial provider initiation, repeated repository scans, event-loop work, and a global cap can dominate cycle duration. The current 100-call global safety ceiling also prevents the load script from exercising 1,000 simultaneous initiations. Before increasing limits, measure end-to-end latency and queue age, optimize indexed reads, use bounded concurrency, and validate atomic capacity reservations under contention.
- **10,000 agents:** a single campaign loop and process-local campaign/event state become operational bottlenecks; provider/API rate limits, database write contention, recovery scans, and hot campaign partitions are likely to fail before the simple pacing arithmetic. Introduce durable event/outbox processing, partitioned campaign work with lease ownership, indexed incremental metrics, bounded provider pools, and tested multi-instance capacity coordination. Preserve a centralized safety budget or a provably safe partitioned budget; never scale by merely increasing the configured call limit.

These are engineering risks inferred from the current prototype, not measured capacity claims. The current Mongo adapter uses per-record compare-and-swap for agent/borrower reservations but does not transactionally commit both reservations, the call record, and provider initiation as one unit.
