# ADR-001: Modular Monolith and Deterministic Core

## Status

Accepted for a local hiring-assignment prototype.

## Context

The system must demonstrate progressive and predictive pacing, safety enforcement, event idempotency, recovery, and a usable dashboard without placing real calls. Correctness under a reproducible local simulation matters more than horizontal deployment throughput.

## Decision

- Use Node.js and strict TypeScript with Express, Zod, Vitest, and Mongoose adapters.
- Keep campaign orchestration, domain state machines, pacing, safety, allocation, providers, recovery, metrics, and simulation in one modular backend.
- Default to in-memory repositories for deterministic single-process runs; keep MongoDB optional for persistence experiments.
- Use a React/Vite dashboard with Recharts for scenario timelines and Lucide icons for controls.
- Provide only deterministic mock provider adapters. Do not configure a real telecom integration.
- Keep predictive pacing read-only and place a separate Safety Controller in front of provider initiation.

## Alternatives Considered

- Redis/Kafka or a distributed workflow service: rejected because they add operational surface without improving the prototype's local acceptance evidence.
- MongoDB as the mandatory source of all coordination: rejected for the simulator path because local tests should not depend on database availability or replica-set setup. Optional Mongoose storage remains available.
- Machine-learning pacing: rejected because the assignment requires an explainable rule-based baseline and there is no trustworthy production dataset.
- Real provider SDK: rejected because all contact must remain simulated.

## Consequences

- The default reservation guarantee applies only within one Node process.
- Mongo compare-and-swap updates prevent duplicate reservation of an individual record, but agent + borrower + call + provider initiation are not one atomic transaction.
- In-memory campaigns, safety decisions, and event audit are lost on restart.
- Simulation is reproducible with fixed seeds, but small outputs are not predictive of production outcomes.
- A production deployment would need durable campaign/event state, cross-entity transaction or saga/outbox semantics, distributed idempotency, observability, authentication/authorization, and provider reconciliation contracts.
